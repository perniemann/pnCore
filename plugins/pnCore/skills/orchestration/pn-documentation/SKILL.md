# Documentation

## When to use

- Whenever creating or updating discovery specs, implementation plans, workflow roadmaps, prior-art research, SVG specs, README, CHANGELOG, or API docs
- When any doc-producing skill (pn-discovery-questionnaire, pn-writing-plans, pn-create-workflow-roadmap, pn-prior-art-research, pn-svg-creator, pn-docs-sync) runs: follow this skill for format compliance

For full document templates and format structures, see [reference.md](reference.md).

## Markdown conventions

- **Heading hierarchy:** Use `#` for title, `##` for major sections, `###` for subsections. Do not skip levels.
- **List style:** Use `-` for unordered lists. Use numbered lists for ordered steps.
- **Code blocks:** Use fenced blocks with language tag. Paths: use forward slashes.
- **Date format:** `YYYY-MM-DD` (ISO 8601).
- **Path patterns:** Use `docs/<type>/YYYY-MM-DD-<slug>.<ext>` for generated docs.
- **Current date:** Use the current date for discovery, plans, and design docs. If the user or context provides today's date (e.g. in AGENTS.md or chat), use that. Do not use stale or assumed dates.

## Project documents

**`workflow_step("project_kickoff")` (canonical):** PRD, design, domain, optional stack/MCP/UI, and the refs index live under **`docs/refs/`**:

- **PRD:** `docs/refs/PRD.md`
- **DESIGN:** `docs/refs/DESIGN-DOC.md`
- **DOMAIN:** `docs/refs/DOMAIN-DOC.md` (when mechanics in scope)
- **STACK / MCP / UI (optional):** `docs/refs/STACK.md`, `MCP-ARCHITECTURE.md`, `UI-DESIGN-SPEC.md`
- **Refs index:** **`docs/refs/README.md`** (not `REF-INDEX.md` for MCP kickoff)

**Legacy flat layout** (older repos): `docs/PRD.md`, `docs/DESIGN.md`, `docs/DOMAIN.md`, `docs/REF-INDEX.md`—preserve if already present; new kickoff flows should use **`docs/refs/`**.

- **WORKFLOW:** `docs/WORKFLOW.md` (from pn-create-workflow-roadmap **after** `pn-writing-plans`; not part of `project_kickoff`)

## Discovery spec

**Save path:** `docs/discovery/YYYY-MM-DD-<slug>.md`

Full format reference: `docs/reference/discovery-and-plan-format.md`

Sections: Technical, Security, Design (3a Direction; when frontend/UI in scope include 3b–3g: Structure and layout, Sections and pages, Colors and theme, Typography, Components and library, Design ambition), Requirements, Scope. Never infer for security; ask or state assumption.

## Plan document

**Save path:** `docs/plans/YYYY-MM-DD-<feature>.md`

Full format reference: `docs/reference/discovery-and-plan-format.md`

Header: Title, Discovery ref, Prior art, Goal, Architecture, Tech stack. Tasks: bite-sized (2–5 min), Files/Steps/Verification per task.

## Workflow roadmap

**Save path:** `docs/WORKFLOW.md`

Generated by pn-create-workflow-roadmap after the plan is written. Maps plan phases to pn-core commands with model tier recommendations and per-step token cost estimates. See [reference.md](reference.md) for full structure template and token cost reference table.

## Prior-art research

**Save path:** `docs/research/YYYY-MM-DD-<slug>-prior-art.md`

Sections: Candidates table (Name, Repo/package, Stars, License, Fit, Pros, Cons), Recommendation (Adapt or Build from scratch with one-sentence justification). Full template in [reference.md](reference.md).

## SVG spec

**Save path:** `docs/svg/YYYY-MM-DD-<slug>-spec.md`

Sections mirror the pn-svg-creator questionnaire: Purpose, Identity, Style, Animation, Colors, Size, Constraints. Full template in [reference.md](reference.md).

## README

### Required sections (when applicable)

- **Setup:** Install steps, prerequisites.
- **Environment:** Env vars, `.env.example` reference (never commit secrets).
- **Scripts:** List of npm/pnpm scripts with one-line description.
- **Usage:** How to run, basic workflow.

Keep scannable: short paragraphs, bullet lists, code blocks for commands. No heavy prose.

## CHANGELOG

Format: `## [version] - YYYY-MM-DD` with sections Added / Changed / Fixed / Removed / Security. One entry per line; user-facing changes only. Full template in [reference.md](reference.md).

## API docs

- **JSDoc/TSDoc:** Document all public surfaces (functions, classes, params, returns). Use the project's existing convention.
- **New or changed endpoints:** Add or update entries. Include path, method, params, response shape, and example.
- **Consistency:** Match the format and style of existing API docs in the project.

## Output

When invoked: return or apply the format rules above. Doc-producing skills reference this skill via `get_skill("pn-documentation")` before writing.

## Guardrails

- Do not invent sections that the doc type does not require.
- Preserve existing content when updating; change only what the feature/fix affects.
- Paths are relative to workspace root.
